### 10. Redis 分布式缓存（Step 18，Cache-Aside 落地）

`OrderService.GetByIdAsync` 是完整的 Cache-Aside 实现：

```csharp
// 1. 查缓存（IDistributedCache，Redis 实现）
var cachedOrder = await _cache.GetStringAsync(cacheKey);
if (cachedOrder == NullCacheValue) return null;        // 空值缓存命中 → 直接返回不存在
// 2. 未命中 → 查库
var order = await _repository.GetByIdAsync(id);
if (order is null) {
    await _cache.SetStringAsync(cacheKey, NullCacheValue,   // 写空值缓存 60s 防穿透
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = NullCacheDuration });
    return null;
}
// 3. 回写缓存（2 分钟）
await _cache.SetStringAsync(cacheKey, JsonSerializer.Serialize(detail),
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = OrderCacheDuration });
```

要点：
- **注册**：`AddStackExchangeRedisCache(o => { o.Configuration = redisConnection; o.InstanceName = "OrderManagement:"; })`
- **三档缓存策略**（对话中确立的企业标准）：普通系统 Cache-Aside+TTL / 中大型 +MQ 重试删除 / 核心业务 Outbox+MQ
- **空值缓存（Null Cache）防穿透**：不存在的 id 也缓存（`"__NULL__"`，60s），防止恶意 id 打穿数据库
- **缓存删除失败处理**：DB 是事实源，删缓存失败不回滚；有限重试（3 次、`Task.Delay(200*attempt)` 退避）+ `LogError`
- **一致性演进路径**：TTL 兜底 → 删除重试 → **Transactional Outbox**（业务数据与消息同事务提交，`BackgroundService` 扫描投递，解决「DB 成功但消息丢失」双写问题）
- **更新/删除后主动失效**：`UpdateAsync`/`DeleteAsync` 成功后 `_cache.RemoveAsync(GetCacheKey(id))`

### 12. 测试体系（Step 21，单测 + 集成测试）

**单元测试**（`Services/Orders/OrderServiceTests.cs` 等）：
- Moq：`Setup(x => x.AddAsync(It.IsAny<Order>())).Callback<Order>(o => savedOrder = o)` + `Verify(..., Times.Once)`
- `NullLogger<OrderService>.Instance` 免日志；InMemory Provider + `Guid.NewGuid()` 库名隔离
- 覆盖：创建、缓存未命中查库回写、缓存命中、空值缓存、更新删缓存

**集成测试**（`OrdersApiTests.cs` + `CustomWebApplicationFactory.cs`）：
- `WebApplicationFactory<Program>` 启动真实 HTTP 管道（需 `public partial class Program { }` 暴露顶级语句 Program）
- 覆盖状态码矩阵：**404 / 201 / 400 / 401 / 403 / 200**
- **三个关键排错**（面试可讲的排障故事）：
  1. `JWT 配置缺失` → `UseEnvironment("Testing")` 不加载 User Secrets → 用 `builder.UseSetting("Jwt:Issuer", ...)` 注入
  2. **EF Core 双 Provider 冲突**（`Only a single database provider can be registered`）→ 必须 `RemoveAll<IDbContextOptionsConfiguration<ApplicationDbContext>>()` 才能移除残留的 `UseNpgsql()`
  3. **测试触发 429** → TestServer 所有请求同一 IP 撞上限流 → `IsEnvironment("Testing") ? 1000 : 5` 放宽测试额度
- `services.RemoveAll<IDistributedCache>(); services.AddDistributedMemoryCache();` 用内存缓存替代 Redis

### 13. Docker 化与 Compose（Step 20）

- **多阶段 Dockerfile**：`sdk:10.0` 编译（先 COPY csproj 再 restore 利用缓存层）→ `aspnet:10.0` 运行，`ASPNETCORE_HTTP_PORTS=8080`
- **容器内配置**：User Secrets 进不了容器，必须用环境变量（`Jwt__SecretKey` 双下划线映射 `:`）；Compose 用 `.env` 插值
- **网络**：服务名即主机名（`Host=postgres`、`redis:6379`），容器内 `localhost` 是自己
- **`depends_on.condition: service_healthy`** + `healthcheck`（`pg_isready` / `redis-cli ping`）保证启动顺序
- **数据卷迁移**：先 `pg_dump` 备份 → `docker stop/rm`（**严禁 `docker compose down -v`**）→ `up -d --build`；`external: true` 复用已有匿名卷
- 坑：compose.yaml 位置要与 build context 匹配；`container_name` 冲突先删旧容器

### 14. 限流 + CORS + 健康检查（Step 19.3/19.5）

```csharp
// 限流：按 IP 固定窗口，5 次/分钟，超限 429
options.AddPolicy("order-api", ctx => RateLimitPartition.GetFixedWindowLimiter(
    partitionKey: ip, _ => new FixedWindowRateLimiterOptions {
        PermitLimit = permitLimit, Window = TimeSpan.FromMinutes(1), QueueLimit = 0 }));
// 控制器：[EnableRateLimiting("order-api")]

// 健康检查：live 只查进程，ready 查 PostgreSQL + Redis
app.MapHealthChecks("/health/live", new() { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = c => c.Tags.Contains("ready") });
```

- **Liveness vs Readiness**：DB 挂了 live 仍 200、ready 503 —— K8s Probe 与负载均衡的依据
- `PostgreSqlHealthCheck`：`Database.CanConnectAsync()`；`RedisHealthCheck`：写→读→比对一次真实验证
- **CORS 白名单**：`WithOrigins("http://localhost:5173", "http://localhost:3000")`，禁用 `AllowAnyOrigin`
- **HSTS 只在非 Dev 启用**（初版写反了，Review 时修正）；管道顺序 `UseRouting → UseCors → UseRateLimiter → UseExceptionHandler → UseAuthentication → UseAuthorization → MapControllers`

### 15. 乐观并发控制（Step 23，xmin 方案）

```csharp
// 实体 + Fluent API（Npgsql 把 uint Version 映射到系统列 xmin，无需 migration）
public uint Version { get; set; }
modelBuilder.Entity<Order>().Property(o => o.Version).IsRowVersion();

// Service 双重检查
if (order.Version != request.Version) throw new DbUpdateConcurrencyException("订单已被其他用户修改，请刷新后重试。");
try { await _repository.UpdateAsync(order); }
catch (DbUpdateConcurrencyException) { throw new DbUpdateConcurrencyException("..."); }  // 兜底时间窗口冲突

// Controller 转 409
catch (DbUpdateConcurrencyException ex) { return Conflict(new { message = ex.Message }); }
```

- UPDATE 生成 `WHERE "xmin" = 旧值`，影响 0 行 → 抛异常；`UpdateOrderRequest.Version` 用 `uint?` + `[Required]` 区分「未传」
- **排障故事**：GET 返回 `version:0`、`createdAt:0001-01-01` → 根因是 Redis 旧缓存（旧 DTO 无 Version 字段）+ DTO 映射漏赋值，不是缺列
- InMemory Provider 没有 xmin，**单测无法验证并发**，需集成测试或真库
