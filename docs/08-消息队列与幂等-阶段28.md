## 一、数据库进阶（阶段 27 收尾）

### 1. 连接池与连接耗尽（27.4）

**核心结论：DbContext 生命周期 ≠ 连接占用时间** —— 查询结束连接即归还连接池，`await using`/Dispose 释放的是 Context 不是独占连接。

**耗尽五因**：
1. 连接泄漏（异常路径没释放）
2. **长事务**（事务持有连接直到 Commit/Rollback）
3. 慢 SQL / 缺索引扫描
4. **事务内做外部 HTTP 调用**（连接被网络往返白白占用）
5. 并发超过 `Maximum Pool Size`

Npgsql 连接串关键键：`Maximum Pool Size`（默认 100）、`Timeout`（获取连接超时）。

### 2. 事务边界：外部调用不进 DB 事务（27.5）

**坏示例**（面试题答 B 的反例）：
```csharp
await using var tx = await _db.Database.BeginTransactionAsync();
await _paymentClient.PayAsync(orderId, amount);   // ❌ HTTP 可能几秒~几十秒，连接被占死
await _db.SaveChangesAsync();
await tx.CommitAsync();
```

**改造版**：
```csharp
// 1. 查询（AsNoTracking，不占事务）
var order = await _db.Orders.AsNoTracking().FirstAsync(x => x.Id == id);
// 2. 外部调用（无事务、无连接）
await _paymentClient.PayAsync(order.Id, order.TotalAmount);
// 3. 短事务只做 DB 写
await using var tx = await _db.Database.BeginTransactionAsync();
order.MarkPaid();
await _db.SaveChangesAsync();
await tx.CommitAsync();
```

> **原则**：事务只包 DB 操作；外部 I/O 放事务外，失败用补偿/状态机回滚。

## 二、RabbitMQ 消息队列（阶段 28）

### 3. 为什么是 RabbitMQ 而不是 Kafka？（选型）

| | RabbitMQ | Kafka |
| --- | --- | --- |
| 定位 | 业务任务分发（智能路由） | 事件流（日志型、高吞吐） |
| 消费 | 消息被 ACK 后删除 | 按 Offset 持久保留、可回放 |
| 适用 | 订单通知、任务队列 | 埋点、事件溯源、流计算 |

> 一句话：**要路由与即发即消用 RabbitMQ，要回放与高吞吐事件流用 Kafka。**

### 4. 五核心概念 + 四种 Exchange

```
Producer → Exchange --(Binding/RoutingKey)--> Queue → Consumer
```

| Exchange 类型 | 路由规则 |
| --- | --- |
| **Direct** | RoutingKey 精确匹配（本项目用这个） |
| **Topic** | 通配：`*` 一个词、`#` 零或多词 |
| **Fanout** | 广播到所有绑定队列 |
| Headers | 按消息头匹配（少用） |

- 端口：`5672` AMQP、`15672` 管理台；镜像 `rabbitmq:4-management`
- compose 坑：数据卷必须在**最外层 `volumes:`** 声明，否则报 `refers to undefined volume rabbitmq_data`

### 5. Producer（入门版）

```csharp
// RabbitMqOptions ← IOptions（Host/Port/凭据/Exchange/Queue/RoutingKey）
await using var connection = await factory.CreateConnectionAsync(ct);
await using var channel = await connection.CreateChannelAsync(cancellationToken: ct);
await channel.ExchangeDeclareAsync(exchange, ExchangeType.Direct, durable: true, ...);
await channel.QueueDeclareAsync(queue, durable: true, exclusive: false, autoDelete: false, ...);
await channel.QueueBindAsync(queue, exchange, routingKey, ...);
await channel.BasicPublishAsync(exchange, ...);   // 入门版每次建连接 → 生产要复用连接 + Publisher Confirms
```

### 6. Consumer（BackgroundService + 手动 ACK）

```csharp
public class OrderCreatedConsumer : BackgroundService
{
    // BackgroundService 是 Singleton，AddDbContext 的 Context 是 Scoped →
    // 必须用 IServiceScopeFactory 每条消息建作用域！
    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
    ...
}
```

**手动 ACK 与 At-least-once**：
- `autoAck: false` → 处理成功 `BasicAckAsync`；失败 `BasicNackAsync(requeue: false)`
- **数据库事务成功后才 ACK**（先 Commit 再 Ack，否则崩溃会重复消费 —— At-least-once）
- `requeue: true` 死循环风险（毒消息反复回来）；无 DLX 时 `requeue: false` 即**丢消息**
- DLX/DLQ 概念：死信交换机/队列接住 `requeue:false` 的消息（本阶段只留概念）

### 7. 消费幂等（28.x，已实测通过）⭐

**幂等三要素**：唯一业务标识（MessageId / HTTP RequestId）+ DB 唯一约束 + 事务原子性。

```csharp
await using var transaction = await dbContext.Database.BeginTransactionAsync(stoppingToken);

// PostgreSQL：唯一约束冲突会让事务进失败态 → 用 ON CONFLICT DO NOTHING
var inserted = await dbContext.Database.ExecuteSqlInterpolatedAsync($"""
    INSERT INTO "ProcessedMessages" ("MessageId", "ProcessedAt")
    VALUES ({message.MessageId}, {DateTime.UtcNow})
    ON CONFLICT ("MessageId") DO NOTHING
    """, stoppingToken);

if (inserted == 0)   // 受影响行数 = 0 → 重复消息
{
    _logger.LogInformation("Duplicate message detected. MessageId: {MessageId}", message.MessageId);
    await transaction.CommitAsync(stoppingToken);
    await channel.BasicAckAsync(ea.DeliveryTag, false);
    return;
}

// 首次消息：执行真实业务（同事务）→ Commit → ACK
```

**实测**：固定 `TestMessageId` 两次 `POST /api/Message/publish` → 第二次日志 `Duplicate message detected`。

**HTTP 幂等同理**：`DeductStockRequest { Guid RequestId }` + `ProcessedRequests` 唯一索引 + 同事务「记 RequestId → 扣库存 → 存结果」；重试按 `RequestId + Success` 状态判断。

**去重记录与业务操作必须同一事务提交** —— 否则「记了去重但业务没做」或反之。

## 9. 面试速记卡

- 「连接池为什么耗尽？」→ 长事务/慢 SQL/事务内 HTTP/泄漏/超池并发；DbContext 生命周期≠连接占用
- 「事务里能调第三方接口吗？」→ 不能；外部 I/O 出事务，短事务只包 DB
- 「RabbitMQ vs Kafka？」→ 任务路由 vs 事件流回放
- 「消息消费怎么保证幂等？」→ MessageId + 唯一索引 + `ON CONFLICT DO NOTHING` 同事务 + 影响行数判重
- 「ACK 时机？」→ 业务事务 Commit 成功后才 Ack（At-least-once + 幂等 = 等效恰好一次）
- 「BackgroundService 里能直接注入 DbContext 吗？」→ 不能（Singleton vs Scoped），用 `IServiceScopeFactory`
