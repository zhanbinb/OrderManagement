## 一、请求管线：中间件（阶段 26.1~26.2）

### 1. 洋葱模型

```
请求 → Use1 → Use2 → Use3 → Endpoint → 响应
              ←──────┴──────┘（next() 之后逆序执行后半段）
```

- **`await next()` 之后的代码在响应阶段逆序执行**（本项目 `RequestTimingMiddleware` 用 Stopwatch 计 total 时间就靠这个）
- **不调用 `next()` = 短路**：403 拦截、限流拒绝、缓存命中直接返回都用这招

### 2. Use / Run / Map

| 方法 | 语义 |
| --- | --- |
| `app.Use(...)` | 续行，可调 `next()` 继续管道 |
| `app.Run(...)` | **终止**管道（不再有后续） |
| `app.Map(...)` | 按路径前缀**分支**（如 `/health` 独立分支） |

- **自定义中间件模板**：`RequestDelegate _next` 构造注入 + `InvokeAsync(HttpContext context, ...)`；**Scoped 依赖必须作为 InvokeAsync 参数注入**（中间件是 Singleton，直接构造注入 Scoped 会 captive dependency）

### 3. 中间件 vs 过滤器（面试二选一高频）

| | Middleware | Filter |
| --- | --- | --- |
| 管辖范围 | **整个 HTTP 管道**（所有请求，含静态资源） | **仅 MVC Action**（路由命中后） |
| 典型用途 | 计时、限流、CORS、认证、异常 | 参数校验、日志、缓存、Action 级授权 |
| 结论 | **异常处理以 Middleware 为主**（`UseExceptionHandler`）、Filter 为辅；两者配 `AddProblemDetails()` | |

**分工口诀：Middleware 管请求、Filter 管 MVC、业务归 Service。**

### 4. 五种 Filter 与执行顺序

```
Authorization → Resource → Action → Exception → Result
```

| Filter | 职责 | 注册 |
| --- | --- | --- |
| Authorization | 授权 | `[Authorize]` 体系 |
| Resource | 资源级（ ViewBag 等） | `IResourceFilter` |
| **Action** | **Action 前后**（本项目 `ActionLogFilter : IAsyncActionFilter`，`await next()` 前后打日志 + 计时） | `[ServiceFilter(typeof(T))]` 需 DI 注册 / `[TypeFilter(typeof(T))]` 自动激活 |
| Exception | Action 异常（`GlobalExceptionFilter : IExceptionFilter`，`context.ExceptionHandled = true`） | `IExceptionFilter` |
| Result | ActionResult 前后 | `IResultFilter` |

- **全局 Filter**：`builder.Services.AddControllers(o => o.Filters.Add<T>())`
- 401 未认证 / 403 无权限 / 404 不存在（语义别混）

## 二、数据库进阶（阶段 27.1~27.3）

### 5. 事务隔离级别（PostgreSQL 实测）

| 级别 | 能防 | PG 默认 |
| --- | --- | --- |
| Read Committed | — | ✅ **默认**：每条 SQL 重新取快照（B 提交后 A 再读能看到 800） |
| **Repeatable Read** | 不可重复读 + **幻读**（PG 实现里也防） | 事务内快照一致（两次读都是 1000） |
| Serializable | 全部 | 需**应用层重试**（序列化失败异常） |

### 6. EF Core 事务用法

- **单次 `SaveChangesAsync()` 自带隐式事务**（多实体变更一次提交）
- 多次写入/多步骤必须显式：

```csharp
await using var tx = await _context.Database.BeginTransactionAsync(ct);
try { /* 多次 SaveChanges */ await tx.CommitAsync(ct); }
catch { await tx.RollbackAsync(ct); throw; }
```

- **事务内禁止 HTTP 调用**（连接被占死，见 [08 篇 §一](08-消息队列与幂等-阶段28.md)）

### 7. 锁与防超卖（面试必考）

| 方案 | 写法 | 适用 |
| --- | --- | --- |
| **原子 UPDATE（首选）** | `ExecuteUpdateAsync` / `UPDATE ... SET stock=stock-@q WHERE id=@p AND stock>=@q`，**按受影响行数判断**（0 行 → 库存不足） | 高并发扣减 |
| 悲观锁 | `SELECT ... FOR UPDATE` | 冲突极频繁 |
| 乐观锁 | `version=1` 条件更新（本项目 xmin 方案） | 冲突少 |

- **死锁**：统一加锁顺序；捕获 `SQLSTATE 40P01`（53P01/deadlock detected）做重试
- ⚠️ 面试纠错：多实例下 `lock` **无效**（进程内锁）→ 必须原子 UPDATE 或 DB 锁

### 8. 索引与慢 SQL（EXPLAIN 实测）

```sql
EXPLAIN ANALYZE SELECT ... -- 实测输出 Seq Scan + Sort → 缺索引
CREATE INDEX idx_orders_created_at ON "Orders"("CreatedAt" DESC);   -- EF: HasIndex().IsDescending(...)
```

- **索引失效**：`LOWER(col)` 函数 → 表达式索引；`LIKE '%xx'` 前置通配 → 全文检索/转向
- **深分页**：`OFFSET 100000` 越翻越慢 → **Keyset 分页** `WHERE ("CreatedAt","Id") < (@last, @lastId) ORDER BY ... LIMIT 20`
- **覆盖索引**：查询列全在索引（PG `INCLUDE`）免回表；**部分索引** `WHERE Status = 1` 只索引热点数据
- **B+Tree vs B-Tree**：B+Tree 叶子链表有序范围扫描；**InnoDB 聚簇索引叶子存行数据**（二级索引要回表），**PG 无聚簇**（heap 存行，索引存 TID 需回表）
- 联合索引最左前缀：`(UserId, Status, CreatedAt)` 顺序按区分度与查询模式设计

## 三、面试速记卡

- 「洋葱模型？→ `next()` 后逆序、不调即短路」
- 「Middleware 和 Filter 怎么选？」→ 管道级用 Middleware（异常/限流/计时），Action 级用 Filter（日志/校验/缓存）
- 「异常用 Middleware 还是 Filter？」→ 以 Middleware 为主（`IExceptionHandler` + ProblemDetails），Filter 辅助
- 「PG 默认隔离级别？」→ Read Committed（每语句新快照）；RR 防幻读；Serializable 要重试
- 「怎么防超卖？」→ 条件原子 UPDATE 按受影响行数（多实例有效）；FOR UPDATE 悲观 / version 乐观
- 「深分页优化？」→ Keyset（游标）代替 OFFSET
- 「索引失效场景？」→ 函数包列、前置 `%`、隐式转换 → 表达式索引/改写查询
