## 二、高级岗位技术知识点地图

### 1. C# 与 .NET 运行时（面试第一优先级）

| 主题 | 必须能讲清楚的点 |
| --- | --- |
| **async/await 与线程池**（对话 13 指定的下一主题） | 状态机编译原理、`SynchronizationContext`、`ConfigureAwait(false)`、线程池饥饿（`Task.Run` 滥用/同步阻塞）、`ValueTask` vs `Task`、`IAsyncEnumerable` |
| 内存与 GC | 分代 GC、LOH、`Span<T>/Memory<T>` 零分配、对象池、`IDisposable` vs `IAsyncDisposable` |
| 泛型与委托 | 协变逆变、`Func/Action`、表达式树、Source Generator（替代反射） |
| 集合与并发 | `ConcurrentDictionary`、`Channel<T>`（生产者-消费者）、`lock` vs `SemaphoreSlim` vs `Mutex`、不可变集合 |
| 语言特性 | record/`init`、模式匹配、`required`、顶级语句（本项目已用） |

**本项目练兵点**：`OrderService` 的 async 链路、`BackgroundService`（Outbox 讨论）、限流器的分区回调。

### 2. ASP.NET Core 深入

- **请求管线全图**：本项目已实践 `UseRouting → UseCors → UseRateLimiter → UseExceptionHandler → UseAuthentication → UseAuthorization → MapControllers`，要能解释每一段的时机与为什么这个顺序
- 中间件 vs 过滤器（Filter 四级：Authorization → Resource → Action → Exception）
- Endpoint Routing、Minimal API vs Controller 选型
- Kestrel 配置、HTTP/2、SignalR（实时通知场景）
- Model Binding / Validation 管道（`[ApiController]` 自动 400 的原理）

### 3. 数据库与 EF Core（面试必考）

- **EF Core 性能**：ChangeTracker 开销与 `AsNoTracking`、`QueryTrackingBehavior`、编译查询、批量操作（`ExecuteUpdate/ExecuteDelete`，.NET 8+）、N+1 识别、`ToQueryString`/`EXPLAIN ANALYZE`（本项目已用）
- **SQL 索引**：B+树、最左前缀、覆盖索引、回表、索引失效场景（函数/前置 `%`/隐式转换）、联合索引设计（本项目有 `OrderNo` 唯一索引可扩展讲）
- **事务**：ACID、隔离级别（Read Uncommitted → Serializable）、**PostgreSQL MVCC** 与 Oracle/MySQL 差异、幻读 vs 不可重复读、死锁与重试
- **并发控制**：悲观锁（`FOR UPDATE`）vs 乐观锁（本项目 xmin 方案 + SQL Server RowVersion 对比）、`DbUpdateConcurrencyException` 处理
- 分库分表、读写分离、Keyset 分页 vs Offset 分页（本项目对话 3 已涉及）

### 4. 缓存与一致性（本项目强项，可深讲）

- 三档策略：Cache-Aside+TTL → +MQ 重试 → Outbox+MQ+幂等（[进阶篇 §10](02-工程化进阶-Step18-24.md)）
- 空值缓存防穿透 / 热点 key 击穿（互斥重建）/ 过期时间加抖动防雪崩
- Redis 深入：数据结构选型（String/Hash/ZSet/Stream）、持久化 RDB/AOF、主从/哨兵/Cluster、大 key 与热 key
- 本地缓存 vs 分布式缓存（`IMemoryCache` 多实例不一致）

### 5. 消息与分布式

- MQ 选型：RabbitMQ（路由灵活）vs Kafka（高吞吐日志）vs RocketMQ（事务消息）
- **可靠投递三问**：不丢（Producer 重试+Broker 持久化+Consumer ACK）、不重（消费幂等，本项目对话 13 已设计 IdempotencyRecord）、有序（分区 key）
- 分布式事务：2PC → TCC → SAGA → 本地消息表/Outbox（本项目已学 Outbox）；最终一致性思维
- 分布式锁：Redis SETNX + 过期 + Lua 释放、Redlock 争议、与 ZooKeeper 对比
- 微服务：gRPC vs REST、服务发现（Consul/etcd——你有 etcd 笔记）、API Gateway、熔断限流（Polly）

### 6. 架构设计

- **DDD**：限界上下文、聚合根、领域事件（订单状态机是天然案例）、充血模型 vs 失血模型
- Clean Architecture / 整洁架构依赖规则；CQRS 读写分离
- SOLID 在本项目的体现（D：`IOrderRepository` 依赖倒置已实践；O：策略授权可扩展）
- 设计模式高频：策略、模板方法、仓库、装饰器（日志/缓存横切）

### 7. 可观测性与 DevOps

- 三支柱：Logs（本项目 Serilog 结构化）+ Metrics（`dotnet-counters`/Prometheus）+ Traces（OpenTelemetry → Jaeger）
- 健康检查分级（本项目 live/ready 已实践）→ K8s Liveness/Readiness/Startup Probe
- CI/CD 进阶：本项目 Actions 三步 → 加 CodeQL 门禁、覆盖率（coverlet 已引入）、制品发布、蓝绿/金丝雀
- 容器进阶：镜像瘦身（多阶段已做）、非 root 用户、资源 limits

### 8. 安全

- OWASP Top 10 与本项目对照：注入（参数化查询/EF 已防）、失效认证（JWT 已做）、敏感数据暴露（user-secrets 已做）、CSRF（API + JWT 天然免疫，要会解释）、日志伪造（CodeQL 已扫出待修）
- OAuth2.0 / OIDC 流程、Access+Refresh Token 轮换、JWT vs Session 选型
- 密码存储：`PasswordHasher`（PBKDF2）/ bcrypt / Argon2

## 三、2026 面试准备策略

### 1. 面试形式判断（2026 现状）

- **主流三段**：八股/基础深挖（1~2 轮）→ 算法（LeetCode Medium，手撕或 AI 辅助白板）→ 项目深挖 + 系统设计
- **AI 工具已是变量**：很多公司允许/默许面试中用 Copilot 类工具 —— 「用 AI 写代码」本身不再是区分度，**「能讲清楚 AI 生成代码的边界与原理」才是**。准备方向从背 API 转向讲清「为什么」
- 系统设计题权重上升（尤其 3~5 年以上）：常考「设计一个订单系统/秒杀/缓存系统」—— **本项目就是最佳素材**（缓存一致性、乐观并发、幂等、限流全都实打实做过）

### 2. 你的差异化卖点（用本项目讲故事）

| 故事 | 讲法（STAR） |
| --- | --- |
| **缓存一致性方案演进** | 从 TTL → 删除重试 → Outbox，能画出三档方案对比图，说明「按业务等级选型，不追求绝对一致」 |
| **EF 双 Provider 冲突排错** | 现象（500 而非 404）→ 定位（Npgsql+InMemory 同注册）→ 根因（`IDbContextOptionsConfiguration` 残留）→ 修复（RemoveAll）—— 完整的深层排障链 |
| **限流 429 误伤测试** | TestServer 单 IP → 按环境放宽而非删限流，体现「理解设计意图再改」 |
| **xmin 乐观并发排障** | version=0 + createdAt=0001-01-01 → 反推是缓存脏数据而非缺列 —— 逆向思维 |
| **测试矩阵 + CI** | 25 测试覆盖 404/201/400/401/403/200 + Actions 自动跑，讲清 Mock 边界（哪些该 Mock 哪些该真跑） |

> **OrderManagement —— 订单管理 API（.NET 10 / PostgreSQL / Redis / Docker）**
