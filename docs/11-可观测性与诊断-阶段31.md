## 一、可观测性三支柱

| 支柱 | 组件 | 本项目对应 |
| --- | --- | --- |
| **Logs** | `ILogger` / Serilog | 已落地：结构化日志 + 按天滚动文件 |
| **Metrics** | `System.Diagnostics.Metrics` + Prometheus/Grafana | dotnet-counters 采样 |
| **Traces** | `Activity` / OpenTelemetry → Jaeger/Tempo | dotnet-trace 采样 |

> 生产分工：**按需采集**（SSH 进 EC2 / 诊断容器跑工具）vs **常驻监控**（Prometheus/OpenTelemetry）。Trace 不宜长采；Dump 含敏感数据。

## 二、四类故障排查思路

| 故障 | 特征 | 定位手段 |
| --- | --- | --- |
| **CPU 高** | 持续占用 | trace 找热点方法（Left Heavy 视图） |
| **内存泄漏** | 只涨不跌 | 静态 `Dictionary<long,Order>` 无清理、事件未退订 → dump 分析（本阶段跳过实操） |
| **接口慢** | 响应时间长 | **N+1**（100 订单 = 101 次查询）→ SQL/索引；`Include` 或 Select 投影 |
| **线程池饥饿** | 吞吐骤降 | `threadpool-queue-length` 涨而 **CPU 不高** → `.Result`/`.Wait()` 同步阻塞 |

## 三、诊断工具实操

### 1. dotnet-counters（实时指标仪表盘）

```bash
dotnet tool install --global dotnet-counters
dotnet-counters ps                                    # 找 PID
dotnet-counters monitor --process-id <PID> System.Runtime
```

**关键指标**：
- `cpu-usage`、`working-set`（内存）
- `gc-heap-size`、`allocation-rate`（分配速率 → GC 压力）
- `threadpool-thread-count`、**`threadpool-queue-length`**（队列涨 + CPU 低 = 饥饿）

实测：PID 62725、`dotnet.assembly.count`=161、`gc.heap.total_allocated`≈15.6MB。

### 2. dotnet-trace（采样调用栈）

```bash
dotnet-trace collect --process-id <PID> --duration 00:00:30 --output ordermanagement.nettrace
dotnet-trace convert --format Speedscope ordermanagement.nettrace   # → speedscope.app 打开
```

- Speedscope 选 **Left Heavy** 视图看「谁最耗时」的采样调用栈
- 本项目已产出 `ordermanagement.nettrace`（16.9MB/30s）+ `.speedscope.json`

### 3. 其余工具

- `dotnet-dump`：抓堆转储分析内存（本阶段跳过，知道用途即可）
- Rider Profiler：IDE 集成的 CPU/内存热点分析（图形化）

## 四、性能优化顺序（面试答题框架）

```
1. 先 Metrics/Tracing 定位（不猜）
2. SQL/索引（N+1、缺索引、深分页）
3. EF 层：AsNoTracking + Select 投影 + Take(20) / Keyset 分页
4. Redis Cache-Aside（已实践）
5. 消除同步阻塞（.Result/.Wait → 全链路 async）
6. 对象分配（allocation-rate 高再优化）
```

## 五、发布与部署（阶段 31 后半）

### 1. build vs publish

| 命令 | 产物 |
| --- | --- |
| `dotnet build` | 编译产物，仅本机可跑 |
| `dotnet publish -c Release -o ./publish` | 发布产物 |

- **Framework-dependent**（依赖安装的 .NET 运行时，体积小）vs **Self-contained**（自带运行时，`-r linux-arm64 --self-contained true`，RID 决定目标平台）
- Docker 多阶段构建属于 Framework-dependent（基础镜像 `aspnet:10.0` 自带运行时）

### 2. 环境与 Secret

- `ASPNETCORE_ENVIRONMENT` ↔ `appsettings.{Development|Staging|Production}.json`
- **密码走环境变量 / 云 Secret Manager，绝不进 Git**（本项目 user-secrets + compose `.env`）

### 3. 三大发布策略

| 策略 | 特点 |
| --- | --- |
| Rolling 滚动 | 逐台替换，平稳 |
| **Blue-Green 蓝绿** | **回滚最快**（切流量即可），但要求 **DB 兼容** |
| **Canary 金丝雀** | 5% → 20% → 50% → 100% 灰度放量 |

### 4. Expand-Contract（无停机迁移数据库变更）

```
1. 加兼容新字段（Expand）→ 2. 切代码读新字段 → 3. 迁数据 → 4. 删旧字段（Contract）
```

> 先加后删、中间态两套都兼容 —— 避免发布窗口期新旧代码同时跑时读到不存在的列。

## 六、面试速记卡

- 「四类生产故障怎么查？」→ CPU 高找热点（trace）、内存涨查静态持有/事件退订（dump）、接口慢查 N+1/索引、**队列涨+CPU 低=线程池饥饿**
- 「dotnet-counters 看什么？」→ cpu-usage / allocation-rate / **threadpool-queue-length**
- 「trace 怎么用？」→ collect 30s → convert Speedscope → Left Heavy 找热点
- 「蓝绿发布前提？」→ DB 兼容（配 Expand-Contract），否则回滚不了
- 「数据库变更怎么无停机？」→ Expand-Contract 四步
