## 一、分布式事务（阶段 29）

### 1. 三方案对比

| 方案 | 机制 | 特点 |
| --- | --- | --- |
| **2PC** | 协调者两阶段提交 | 同步阻塞、协调者单点；数据库层面尚可用，跨服务少用 |
| **TCC** | Try（预留）/ Confirm / Cancel | 业务层面侵入大，资源预留 |
| **Saga** | 本地事务 + **补偿操作** | 最终一致；补偿是**新业务操作而非回滚** |

**Saga 补偿落地要点**（面试高频追问）：
- 库存补偿用**增量 UPDATE**（`AvailableStock = AvailableStock + 2`），不能覆盖历史值（10→8→恢复成 10 会吞掉别的订单扣减）
- 配套 `InventoryTransactions` 流水表 + `InventoryCompensations` 表 `UNIQUE(OrderId, Action)` 幂等，**补偿与记录插入同事务**
- 冻结库存模型：`AvailableStock` / `FrozenStock` 分列
- **自动为主、人工兜底**

### 2. Outbox Pattern（可靠发布）⭐

```
业务事务：BEGIN → INSERT Orders + INSERT OutboxMessages(Status=Pending) → COMMIT
BackgroundService：扫描 Pending → 发 MQ → 改 Published（失败保留重试）
消费端：MessageId 唯一索引幂等（见 08 篇）
```

- 解决「DB 成功但 MQ 发送失败」双写问题
- **Outbox 只保证可靠发布，不保证只发一次** —— 消费端幂等是配套必备
- 还需：Publisher Confirms、并发扫描认领、失败重试记录

## 二、服务间通信与容错

### 3. 通信选型

| 方式 | 场景 |
| --- | --- |
| HTTP REST | 简单、通用、需同步响应 |
| **gRPC**（HTTP/2 + Protobuf） | 内部高性能二进制调用 |
| RabbitMQ | 异步、无需即时响应 |

### 4. 容错四件套

| 组件 | 要点 |
| --- | --- |
| **Timeout** | `CancellationTokenSource` 3 秒硬超时 |
| **Retry** | 指数退避 1/2/4s + Jitter；**HTTP 400 与库存不足不重试**（非瞬时错误） |
| **Circuit Breaker** | Closed → Open → Half-Open 三态 |
| **Fallback** | 降级返回默认值/缓存 |

```csharp
// .NET 生态标准实现：Microsoft.Extensions.Http.Resilience
builder.Services.AddHttpClient("InventoryClient", ...)
    .AddStandardResilienceHandler();   // 超时/重试/熔断一体化
```

## 三、微服务架构

- **拆分原则**：按业务领域 / Bounded Context，**不是按 Controller 技术层**
- **API Gateway 职责**：路由、JWT 认证、限流、负载均衡、协议转换；.NET 生态选 **YARP**（官方）或 Ocelot
- **架构匹配业务规模**：小团队优先**模块化单体**，不要为了微服务而微服务

## 四、SOLID 与设计模式（阶段 30）

### 5. SOLID 要点

- **DIP 依赖倒置**：Domain 定义接口、Infrastructure 实现、组合根注册（本项目 DDD 即实践）
- **策略选择用 Keyed DI 替代 if/else**：

```csharp
builder.Services.AddKeyedScoped<IDiscountStrategy, VipDiscount>("VIP");
// 解析：IServiceProvider.GetRequiredKeyedService<IDiscountStrategy>("VIP")
```

### 6. 四大模式口诀

> **工厂（创建）、策略（选择）、模板方法（流程）、装饰器（增强）**

**装饰器**（面试常让手写思路）：

```csharp
public class LoggingOrderService : IOrderService
{
    private readonly IOrderService _inner;               // 持有下一层
    public LoggingOrderService(IOrderService inner) => _inner = inner;
    public async Task<Order> CreateAsync(...)
    {
        _logger.LogInformation("before"); var r = await _inner.CreateAsync(...);
        _logger.LogInformation("after"); return r;
    }
}
// 不改原类，叠加日志/缓存 —— 组合优于继承；每层实现同一接口
```

**补充模式**：观察者（事件）、责任链（**Middleware Pipeline 就是责任链**）、代理（Castle DynamicProxy）—— 代理与装饰器区别：**控制访问 vs 增加功能**。

## 五、三大架构模式对比

| 架构 | 结构 | 要点 |
| --- | --- | --- |
| 三层 | UI → BLL → DAL | 传统，层内依赖向下 |
| **Clean Architecture** | API → Application → **Domain** ← Infrastructure | **DIP 是基础**；依赖只指向内层 |
| **CQRS** | Command 与 Query 分离 | 可共用 PostgreSQL；**≠ Event Sourcing** |

## 六、面试速记卡

- 「分布式事务怎么选？」→ 简单本地消息表/Outbox；要预留资源 TCC；长流程跨服务 Saga（补偿是增量新操作不是回滚）
- 「Outbox 解决什么？」→ 双写一致性；只保证可靠发布，消费端幂等配套
- 「服务调用失败怎么办？」→ Timeout+Retry（区分瞬时错误）+Circuit Breaker+Fallback；`AddStandardResilienceHandler`
- 「微服务怎么拆？」→ 按业务边界渐进拆；小团队先模块化单体
- 「装饰器 vs 代理？」→ 增加功能 vs 控制访问；装饰器每层同接口 + `_inner`
- 「CQRS 和 Event Sourcing 一样吗？」→ 不一样；CQRS 只是读写模型分离
